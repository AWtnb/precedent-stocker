# 判例スクレイピング・判例コード計算スクリプト

裁判所の判例検索サイト（courts.go.jp）から判例情報を定期的に取得し、スプレッドシートに蓄積するとともに、取得した情報から判例コードを計算するGoogle Apps Script。

## 概要

`MAIN_SHEET` のA列には、判例ページのURLに使われる番号（10000〜）が入っている。以下の3つの関数が、それぞれ異なる間隔で定期実行される。

- **`scrape`**（数分おき）：1回の実行につき1行ずつ判例ページへアクセスし、判例情報（事件番号・事件名・裁判年月日・裁判所名）をB〜E列に埋めていく
- **`encodePrecs`**（1時間おき）：B〜E列が埋まった行を対象に、判例コードを計算してF列に書き込む
- **`checkSheetFilled`**（任意のタイミング）：F列（判例コード）の充足状況を確認し、進捗をメールで通知する

いずれも行数が数万件規模になる可能性があるため、全列を読み込む方式は避け、必要最小限の列のみを読み込む設計にしている。

## シート構成

### MAIN_SHEET（1枚目のシート）

ヘッダーなし。列の意味は以下の通り。

| 列 | 内容 |
|---|---|
| A | 判例番号（`https://www.courts.go.jp/hanrei/XXXXX/detail7/index.html` の `XXXXX` に該当）。あらかじめ10000〜の数値を入力しておく |
| B | 事件番号 |
| C | 事件名 |
| D | 裁判年月日（和暦） |
| E | 裁判所名 |
| F | 判例コード |

B〜E列は`scrape`によって埋まっていく。**B〜E列は4項目すべて取得できた場合のみ書き込む**（一部だけ取得できても書き込まない）。F列は`encodePrecs`によって埋まっていく。

### LOG_SHEET（2枚目のシート）

A1セルのみ使用する。`scrape`が「次にMAIN_SHEETの何行目から探索を始めるか」を記録する。初回実行時は空欄扱いで、1行目（先頭）から探索する。

### COURT_DATA_SHEET

裁判所マスタデータ。2行目以降にデータが入っている（1行目はヘッダー）。1列目に裁判所名、4列目に裁判所種別（`level`）、5列目にコード、6列目に旧裁判所フラグ、7列目に改廃区分が入っている想定。判例コード計算時に裁判所名から審級別裁判所コードを引くために使用する。

### SIGN_DATA_SHEET

事件符号マスタデータ。2行目以降にデータが入っている（1行目はヘッダー）。1列目に符号（例: `ネ`）、2列目にコードが入っている想定。判例コード計算時に事件番号中の符号からコードを引くために使用する。

## 処理の流れ

### `scrape`関数

1. `LOG_SHEET` のA1を見て、探索を開始する行番号を決める（空欄なら1行目）
2. `MAIN_SHEET` のB列を読み込み、開始行以降で最初に見つかる**空欄の行**を探す（＝A列しか埋まっていない未処理行）
3. 未処理行が見つかった場合
   - その行のA列の値（判例番号）を使い、`https://www.courts.go.jp/hanrei/XXXXX/detail7/index.html` にアクセスする
   - レスポンスが200の場合、HTML内の`meta`タグを解析する
     - ページ本体（判例情報テーブル部分）はJavaScriptで動的に組み立てられるため、レスポンスHTMLを直接パースしても要素を取得できない
     - 一方、`<meta name="xxx" content="yyy">`形式のmeta要素はサーバー側で埋め込まれるため、レスポンスHTMLに確実に含まれている
     - 正規表現で全`meta`要素の`name`と`content`を抽出し、`name`をキーとするマップを作る
     - 以下4つの`name`に対応する値がすべて取得できた場合のみ、B〜E列に書き込む

       | スプレッドシート列 | meta要素のname | 例 |
       |---|---|---|
       | B（事件番号） | `composite_jiken_number` | `平成16(ネ)3324` |
       | C（事件名） | `jiken_name` | `損害賠償請求控訴事件` |
       | D（裁判年月日） | `judge_date_wareki` | `平成16年10月19日` |
       | E（裁判所名） | `court_name` | `東京高等裁判所` |

   - 200以外（404など）の場合や、4項目が揃わなかった場合は何も書き込まない
   - 処理した行番号を `LOG_SHEET` のA1に記録する
     - 処理した行がシートの最終行だった場合、次回の開始行として1行目を記録する（＝先頭に戻る）
4. 未処理行が見つからなかった場合は何もしない（完了通知は`checkSheetFilled`側で行う。詳細は後述）

### `encodePrecs`関数

1. `MAIN_SHEET` のB列（事件番号）とF列（判例コード）のみを読み込み、「B列が埋まっている（＝スクレイピング済み）」かつ「F列が空欄（＝コード未計算）」の行を対象行として抽出する
2. 対象行が1件もない場合はここで終了する
3. `COURT_DATA_SHEET`・`SIGN_DATA_SHEET`のマスタデータを1回だけ読み込む（対象行数に関わらず1回のみ。行ごとに読み直さない）
4. 対象行についてのみ、D列（裁判年月日）・E列（裁判所名）を読み込む
   - 判例コードの計算に事件名（C列）は使用しないため、この読み込み範囲にC列は含めていない
5. 対象行ごとに以下を計算し、いずれかが計算できなければその行はスキップする（次回以降に再チェックされる）
   - 裁判所名 → 審級別裁判所コード（`COURT_DATA_SHEET`を参照）
   - 裁判年月日（和暦） → 元号コード＋年月日8桁
   - 事件番号 → 事件番号コード（`SIGN_DATA_SHEET`を参照）
6. 3つのコードを`-`で連結した文字列を判例コードとし、F列に書き込む
   - 書き込みは対象行1件ごとに`setValue`するのではなく、行番号が連続している範囲ごとにまとめて`setValues`する（詳細は「設計上のポイント」参照）

### `checkSheetFilled`関数

1. `MAIN_SHEET` のF列（判例コード）を全行読み込み、値が入っている最終行（＝どこまで判例コードが発行済みか）を求める
2. その行がシートの最終行と一致していれば「最終行まで判例IDの発行が完了しました」、一致していなければ「◯行まで判例ID発行が済みました」という件名・本文のメールを`MAIL_TO`に送信する
3. 完了・未完了を問わず、呼び出されるたびに必ず1件メールを送信する

## 判例コードの構成

`{裁判所コード}-{年月日コード}-{事件番号コード}` の形式。

- **裁判所コード**：審級コード（1桁）＋旧裁判所フラグ（1桁）＋裁判所コード＋改廃コード（1桁）＋種別コード（1桁、家裁系かどうか）
- **年月日コード**：元号コード（2桁）＋年2桁＋月2桁＋日2桁の8桁
- **事件番号コード**：元号の英字1文字＋年＋事件符号コード＋番号

## 設計上のポイント

### ページ本体ではなくmeta要素から情報を取得する

対象ページは判例情報テーブル部分がJavaScriptで動的に組み立てられる仕様のため、`UrlFetchApp`で取得した生HTMLを解析してもテーブル要素が存在しない。一方、`<meta name="xxx" content="yyy">`形式のmeta要素はサーバー側で生成されHTMLに直接埋め込まれているため、動的レンダリングの影響を受けず確実に取得できる。この特性を利用し、`meta`要素の`name`属性をキーとして必要な値を抽出している。

HTML構造（`dl`/`dt`/`dd`など）のパースが不要になったため、外部ライブラリへの依存はなく、正規表現のみで抽出処理を実装している。

### 404は一時的なものとして扱う

判例番号によっては、その時点でページが未作成のため404になることがあるが、後日ページが作成されることがある。404の場合はB〜E列に何も書き込まないため、該当行は「未処理行」のままとなり、次回以降のループで自動的に再チェック対象になる。同様に、meta要素から4項目が揃わなかった場合も書き込みを行わず、未処理行として残す。

`encodePrecs`側も同様の考え方で、裁判所名や事件番号がマスタデータに一致せずコード計算できなかった行はF列を空欄のままにし、次回実行時に再チェック対象とする。


### メール通知は「全行を1周確認できたとき」のみ送信（`scrape`の探索ロジックについて）

`scrape`が未処理行を探す際、未処理行が見つからないケースには2種類ある。

- 探索開始行が1行目のとき：全行を確認した結果、本当に未処理行が存在しない
- 探索開始行が1行目以外のとき：まだ確認していない前半部分に未処理行が残っている可能性がある

この区別自体は探索ロジックとして`scrape`内に残っているが、現在は完了メールの送信トリガーとしては使用していない（メール通知は`checkSheetFilled`に一元化されているため）。

### パフォーマンス（未処理行のみを対象にした読み書き）

`scrape`・`encodePrecs`ともに、行数が数万件になる可能性を考慮し、全列を`getValues()`で読み込む方式は採用していない。

- `scrape`：未処理判定に必要なB列1列のみを読み込むことで、データ転送量を全列読み込みの場合の1/5程度に抑えている
- `encodePrecs`：まずB列・F列のみを読んで対象行（未計算行）を絞り込み、詳細データ（D・E列）は対象行のみを読み込む。すでにコードが計算済みの行は一切読み書きしない。マスタデータ（`COURT_DATA_SHEET`・`SIGN_DATA_SHEET`）も対象行数に関わらず1回だけ読み込み、行ごとの再読み込みを避けている
- `checkSheetFilled`：F列1列のみを読み込み、値が入っている最終行を特定する

`TextFinder`による空文字セル検索も検討したが、正規表現＋完全一致の組み合わせで空欄セルにマッチしない挙動が確認されたため見送った。列を絞った`getValues()`であれば、2万行規模でも実行時間制限（6分）に対して十分な余裕がある。

### `setValues`のバッチ化

`encodePrecs`で判例コードをF列に書き込む際、対象行1件ごとに`setValue`を呼ぶと、対象行が数千〜数万件ある場合にAPI呼び出し回数が膨らみ実行時間を圧迫する。そのため、対象行の行番号が連続している範囲ごとにグルーピングし、範囲ごとに1回の`setValues`で書き込むことで呼び出し回数を抑えている（対象行が飛び飛びの場合は、連続区間の数だけ呼び出しが発生する）。

### 同時実行の競合について

`scrape`（数分おき）と`encodePrecs`（1時間おき）はいずれも`MAIN_SHEET`に書き込みを行うが、対象列が異なる（`scrape`はB〜E列、`encodePrecs`はF列）ため実用上の実害は小さい想定。`checkSheetFilled`はF列の読み込みのみで書き込みは行わないため、他の2関数との競合は発生しない。ただし、GASの同一プロジェクト内トリガーは基本的に排他制御されないため、厳密な安全性が必要な場合は`LockService`の導入を検討する。

## 必要なスクリプトプロパティ

| キー | 内容 |
|---|---|
| `SHEET_ID` | 対象スプレッドシートのID |
| `DATA_SHEET_ID` | 裁判所コード・事件符号スプレッドシートのID |
| `MAIL_TO` | 完了通知の送信先メールアドレス |

## 依存ライブラリ

なし。meta要素の抽出、判例コードの計算ともに正規表現・標準APIのみで実装している。

## 実行トリガー設定

以下3つの関数に対し、それぞれGASエディタから時間主導型トリガーを設定する。コード側でのトリガー登録処理は行っていない。

| 関数 | 間隔 |
|---|---|
| `scrape` | 分ベース（数分おき） |
| `encodePrecs` | 時間ベース（1時間おき） |
| `checkSheetFilled` | 任意のタイミング（呼び出しごとに必ずメールを送るため、高頻度設定は避ける。1日1回程度を推奨） |
